# ContextIQ  навигатор по контенту/активностям

## Идея проекта

ContextIQ это веб-сервис, который помогает человеку выбрать, чем заняться в данный момент времени, с учётом его настроения, интересов и тд. Вместо поиска в разных приложениях пользователь может написать что устал и что ему хочеться сейчас. Система будет анализировать контекст и предлагать различные активности.

Наше отличие от обычного чат-бота это единый цикл: состояние -> контекст -> персональная рекомендация -> обратная связь. Пользователь сможет оценивать предложения, а сервис учитывать устойчивые предпочтения, не смешивая их с сиюминутным настроением. Цель проекта - сократить время на поиск контента и помочь людям осмысленно организовывать отдых и досуг.
## 1. Задача, конечный результат и физическая основа

Наша задача разработать и исследовать мультимодальную систему рекомендаций на основе различных входных данных. К концу семестра планируем показать веб-приложение или MVP: пользователь вводит запрос или записывает голос, система выделяет контекст, выдаёт рекомендации, сохраняет предпочтения.

Физическая основа - акустика и цифровая обработка сигналов. Микрофон преобразует колебания звукового давления в цифровые отсчёты, после чего можно вычислять:

- RMS  среднеквадратичную амплитуду сигнала: $x_\mathrm{RMS}=\sqrt{\frac{1}{N}\sum_{n=0}^{N-1}x[n]^2}$;
- FFT частотное представление сигнала (быстрое преобразование Фурье);
- спектральный центроид;
- STFT/спектрограмму изменение частотного состава во времени.

В исследовательской части рассматриваем частоту дискретизации, предел Найквиста, спектральное разрешение и погрешности вычислений. Эти метрики сами по себе не позволяют уверенно определить эмоцию, поэтому мы изучаем их как физические параметры голоса и проверяем, улучшают ли они анализ в сочетании с текстом.

## 2. Что сделано к первому отчёту

Проект разбит на три независимых сервиса и исследовательские модули. Первый вариант Python-сервиса подготовлен; для C# и React сформированы отдельные реализации по архитектуре. Сейчас основной этап проверка фактической интеграции, воспроизводимых экспериментов и устранение ошибок. Ниже описан состав разрабатываемого прототипа, а не заявление о том, что каждая функция уже прошла проверку.

| Компонент | Стек | Назначение | Этап |
|---|---|---|---|
| Физический анализ аудио | Python, NumPy, SciPy | RMS, FFT, спектр, спектрограмма | Первичная реализация и валидация на записях |
| Анализ текста и контекста | Python, FastAPI, AI | Предполагаемое настроение, энергия, темы | Прототип и количественная оценка |
| Сервер и хранение | C#, ASP.NET Core, БД | REST API, профиль, история, связывание сервисов | Сборка и интеграционная проверка |
| Интерфейс | React, TypeScript | Ввод текста/голоса, карточки рекомендаций, графики | Прототип и интеграционная проверка |

Планируемая архитектура:

```text
Пользователь (текст / эмодзи / голос)
                  ↓
         React + TypeScript
                  ↓ HTTP
        C# / ASP.NET Core
          ↙             ↘
 Python / FastAPI      База данных
   ├─ физика звука       ├─ профили
   ├─ анализ текста      ├─ история
   └─ ранжирование       └─ оценки
                  ↓
       Персональные рекомендации
```

## 3. Результаты и способы проверки

Для физического эксперимента выбраны два контрольных сигнала: 440 и 880 Гц.  Для синусоиды единичной амплитуды теоретическое значение RMS составляет $1/\sqrt{2}\approx0{,}7071$. Это пока что расчётные ориентиры.

Проверяемые критерии эксперимента:

1. Правильно ли алгоритм определяет частотные пики синусоид 440 и 880 Гц;
2. Какова абсолютная погрешность: $\Delta f=|f_\mathrm{измер}-f_\mathrm{эталон}|$;
3. Увеличивается ли RMS пропорционально амплитуде;
4. Как изменяются спектры и спектрограммы реальных записей голоса;
5. Каковы точность классификации на размеченных фразах и время ответа сервиса.

К следующему отчету мы планируем уже сделать и приложить: реальные значения из тестовых запусков, диаграммы сигналов, результаты `pytest`/`dotnet test`/frontend-тестов и скриншоты E2E сценария.
